# Operations and recovery

Compose runs PostgreSQL, Redis with append-only persistence, API, worker, a bounded Forge runner, web, bootstrap and metadata maintenance. Bind the web port to localhost or a private trusted network; authentication is intentionally administrative rather than multi-user accounts.

The API persists jobs and immutable execution plans before queue submission. Its ten-second reconciliation loop repairs missing queue submissions. Workers hold PostgreSQL session advisory locks per job, poll cancellation, enforce total job deadlines and checkpoint each actual game/match. BullMQ detects a killed worker's expired lock and resumes it. The worker submits only pending absolute unit indices; independent seeds retain their original indices. A partially played BO3 restarts from its first game because native match/sideboarding history is needed; streamed observations remain auditable and are separate from canonical finalized games. Completed results are never replayed or overwritten.

The bridge has a wall clock per actual game, including setup. Timeouts emit unknown winner/placements and restart their JVM. An external watchdog terminates a process that stalls for 90 seconds at startup/between games or exceeds the game clock by five seconds. Process failures remain errors, never inferred draws or played games. HTTP disconnect/cancellation/shutdown kills the process group, escalating to SIGKILL after three seconds. Job deadlines cover queue recovery elapsed time as well as engine work.

Bootstrap compiles into a temporary directory and atomically publishes an immutable `forge/bridge-builds/<sourceHash>` directory, followed by the manifest. Each runner request captures its manifest and uses that exact directory for every JVM/restart. Refresh cannot replace classes under a running JVM. Old build directories are retained so active executions remain valid; operators may remove unused hashes only after draining jobs. Queued and resumed jobs request their pinned engine version and bridge hash from the runtime registry; archived runtimes are retained.

## Card metadata

The maintenance service checks once per minute whether `cards.json` is older than `CARD_REFRESH_HOURS` (default 24). Refresh runs bootstrap with `--refresh-cards --metadata-only`, a thirty-minute outer process deadline, and a PostgreSQL global advisory lock. The last valid cache remains available if download/validation fails. Scryfall data and Forge facts use atomic file renames. Forge follows the [latest stable release](FORGE_UPDATES.md) through a separate hourly validated update; card refresh does not change the engine.

`POST /api/v1/operations/refresh-cards` requires the admin bearer token and requests immediate refresh (202 accepted, 409 already active). The queue screen has a service-health disclosure and admin refresh control. The API checks cache/bridge modification times every 30 seconds and fully loads a replacement provider before swapping it; failed reloads preserve the old provider and expose an error. Immutable deck versions, snapshots and job provenance retain their original values. Feed imports and new validations use the current provider.

`GET /api/v1/operations` reports job-state counts, runner slot utilization/capabilities/source hash, maintenance state, card-data timestamps/provenance, cache reload errors and feed freshness/errors. `/health` checks API database/Redis; runner/worker/maintenance each expose internal health endpoints. Compose enables bounded container logs. Use `/api/docs` for public API routes, simulation events/observations for progress/audit, and `docker compose logs` for process diagnostics.

## Engine logs

`LOG_FILE_MB=8` bounds each retained engine log; parsing and result collection continue after the diagnostic log cap, with an explicit truncation marker. `LOG_TOTAL_MB=512`, `LOG_MAX_FILES=500`, and `LOG_RETENTION_DAYS=7` bound completed log retention. Retention runs before and after batches, deleting oldest excess/expired logs. Current `.active` logs are excluded; abandoned active files age out after 24 hours. Concurrent processes may temporarily add up to one capped log each beyond completed-log limits. Log write errors are caught/reported rather than crashing on an unhandled stream event. Measurements and provenance remain in PostgreSQL after diagnostic logs expire.

Back up PostgreSQL and runtime metadata (and desired logs) before a host migration. Redis is durable coordination; PostgreSQL is the authoritative job/result record. Keep runtime metadata read-only in API/worker/runner, writable only in bootstrap/maintenance. Do not change Forge release/source while jobs are queued unless intentionally invalidating their unfinished work.

This managed executor has an 8 GB Docker VFS disk. Its live runtime uses bind-mounted cached Forge data and copied compiled artifacts; clean source-image builds are verified in GitHub Actions. Local maintenance acceptance reused the existing runtime image with unchanged cached Java artifacts; the repository's maintenance service uses the full JDK bootstrap image. Session proxy, CA and hostname mapping remain untracked environment configuration. Internal services, including `maintenance`, must be listed in `NO_PROXY` when configuring outbound proxies.
