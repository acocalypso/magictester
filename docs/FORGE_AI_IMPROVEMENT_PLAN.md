# Forge AI improvement plan

Research checked on 7 November 2026. This is an implementation proposal, not a claim that the changes or playing-strength gains have already been delivered. Scope includes all supported formats, deck archetypes, and card/effect types. No finite test suite establishes perfect play for every Magic interaction.

The recommended approach is a shared, versioned Java AI layer around Forge: retain its rules engine, adopt tested upstream AI improvements, and measure playing strength separately from simulation speed. All decisions remain local on Android, Windows, Linux and Docker. Start with bounded search and better heuristics; a trained model is a later experiment.

## What the research establishes

- [Forge's AI documentation](https://github.com/Card-Forge/forge/wiki/AI) describes a heuristic AI with stronger aggro/midrange play and weaker control/combo play. Command-line simulation does not itself imply a smarter decision policy.
- The [latest stable release](https://github.com/Card-Forge/forge/releases/tag/forge-2.0.15) is 2.0.15, published 28 September 2026. MagicTester's Android engine is pinned to source `4ec5f1a2c32fa90ecb983a72b9eb47aa5c5d7676`.
- Both MagicTester bridges explicitly create AI players with the `Default` profile. The [stable player factory](https://github.com/Card-Forge/forge/blob/4ec5f1a2c32fa90ecb983a72b9eb47aa5c5d7676/forge-gui/src/main/java/forge/player/GamePlayerUtil.java) passes null simulation options through that overload. Profiles and simulation algorithms are separate configuration choices.
- Development source was examined at `98d79231ccbe78f0083db907fdc875034665ba38`, committed 7 November 2026. Its [simulation package](https://github.com/Card-Forge/forge/tree/98d79231ccbe78f0083db907fdc875034665ba38/forge-ai/src/main/java/forge/ai/simulation) contains Flat Monte Carlo, deck/Commander plans, combo planning, hidden-information sampling and other capabilities absent from the stable simulation package. Some older full/hybrid simulation machinery already exists in stable; none should be advertised as a newly invented algorithm.
- Recent fixes include [flash ETB timing, PR #12707](https://github.com/Card-Forge/forge/pull/12707) and [planeswalker loyalty, PR #12742](https://github.com/Card-Forge/forge/pull/12742). The associated issues are closed. They illustrate why a newer planner still requires regression tests, not evidence that those exact bugs remain unfixed at the inspected development commit.
- Our [three completed desktop reference games](benchmarks/commander-elves-duration.md) averaged 4m 12.126s, with a longest game of 7m 52.741s. That game recorded 18 internal AI evaluation timeouts. These are observations about this particular workload and desktop runtime, not an Android/phone average. The completed [Android experiment](benchmarks/commander-elves-duration.md) recorded three normal games averaging 19m 28.752s and two 30-minute timeouts. Its overall completion-time average is unknown; these are emulator measurements.

## Ordered implementation work

1. **Establish the comparison harness and AI provenance.** Add explicit policy configuration to both bridge request schemas and exports: algorithm, profile, search budget, policy/patch hash and rules-engine version. Keep the original policy as a frozen baseline. Version the deck corpus and tactical positions independently of the live daily meta. Record each decision's category, elapsed/CPU time, candidate and rollout counts, fallback reason and deadline status, with bounded diagnostics. Never expose opponents' hidden cards in user-facing explanations.

   Done when an archived run identifies the exact AI implementation and can be replayed with the same inputs. Include a fixed-work-budget mode: a seed alone cannot guarantee identical decisions across devices when wall-clock deadlines cut search at different points. Search randomness must not consume the real game's shuffle/draw random stream.

2. **Make AI deadlines safe and useful before deepening search.** Audit the [stable evaluation loop](https://github.com/Card-Forge/forge/blob/4ec5f1a2c32fa90ecb983a72b9eb47aa5c5d7676/forge-ai/src/main/java/forge/ai/AiController.java) against development's [AITimeoutTracker](https://github.com/Card-Forge/forge/blob/98d79231ccbe78f0083db907fdc875034665ba38/forge-core/src/main/java/forge/util/AITimeoutTracker.java). Port a coherent shared deadline through nested choice, combat and mana evaluation; add cooperative checks to measured hot loops. Separate decision, turn, and whole-game budgets.

   Remove reliance on forcibly stopping a worker thread: the source explicitly acknowledges that its fallback is unsupported on Android and modern Java. An evaluation that cannot stop must not keep mutating the live game while another decision proceeds. Prefer isolated planning state and a validated fallback; if consistency cannot be guaranteed, terminate that isolated attempt and retain evidence. Do not fabricate a winner or a rules draw.

   Profile the observed mana-source sorting, alternative-cost and static-ability paths. Cache immutable rules freely, but memoize state-dependent values within a decision or a correctly invalidated game revision, including player/phase/resources/targets in the key. No cache keyed only by card name across changing boards. Preserve the existing process isolation between simultaneous games.

   Done when stress positions respect the shared budget, leave no live mutating evaluation behind, preserve legal state, and show measured tail-latency/allocation improvements. More parallel matches and longer game clocks do not prove this work succeeded.

3. **Evaluate upstream bounded FlatMC as an experimental policy.** Reuse the development planner and its supporting classes/tests as a dependency cluster; do not copy one picker class into 2.0.15 and assume compatibility. Compare heuristic, existing hybrid/full simulation, and bounded FlatMC using identical scenarios and controlled compute budgets. Stable remains the default engine channel. Any backport is identified as stable Forge plus an explicit AI patch, rather than mislabeled as an unmodified stable release.

   The inspected [FlatMonteCarloPicker](https://github.com/Card-Forge/forge/blob/98d79231ccbe78f0083db907fdc875034665ba38/forge-ai/src/main/java/forge/ai/simulation/FlatMonteCarloPicker.java) already has mobile/desktop limits. Its mobile-lite constants include a 600 ms decision budget and 2,500 ms turn budget; these are source settings, not demonstrated latency guarantees. Start from those mechanisms, then calibrate with the actual workload and hardware. Keep bounded heuristic fallbacks and record why they were used. Candidate generation must include plausible legal alternatives beyond what the old heuristic approves, or search can never discover a better line.

   Done when the candidate wins quality tests and the controlled league without unacceptable completion, memory or latency regressions. Allow different validated defaults per platform/archetype; do not declare full simulation universally strongest.

4. **Fix decisions by effect and strategy, with a broad scenario matrix.** Extend existing APIs and upstream [AI tests](https://github.com/Card-Forge/forge/tree/98d79231ccbe78f0083db907fdc875034665ba38/forge-gui-desktop/src/test/java/forge/ai), including Commander, Storm, Standard/Vintage scenarios, mana, flash and planeswalker cases. Port representative fixtures to the Android runtime rather than expecting the desktop test harness to run unchanged. Start with roughly 64 curated positions and expand from actual failures. The following are proposed acceptance cases, not claims about remaining upstream bugs:

   | Coverage | Concrete improvement to verify |
   | --- | --- |
   | Aggro, burn and combat tricks | Take available lethal; preserve blockers against lethal; value haste and temporary control; sequence tricks at useful priority windows. |
   | Tempo and control | Reserve relevant interaction; rank threats by impact rather than mana value alone; compare acting with holding priority/mana; use flash ETB abilities at the right time. |
   | Midrange, ramp and tokens | Develop appropriate mana; value engines and card advantage; assess wipes, token losses and replacement effects; avoid spending resources on actions with no useful effect. |
   | Combo, Storm, tutors and graveyards | Preserve required pieces; search ordered multi-action lines with verified costs and restrictions; recognize interaction and alternative wins. Extend the existing combo catalogue with general search rather than relying on names alone. |
   | Artifacts, enchantments and planeswalkers | Evaluate activated/static/triggered effects; choose useful targets, modes and X; account for loyalty and sacrifice costs; avoid helping an opponent without a strategic benefit. |
   | Commander/cEDH and Duel | Value commander tax, synergy and the applicable damage rules; protect engines; evaluate every opponent's immediate win threats. Test four-player threat assessment separately from two-player Duel. |

   Reuse development's [DeckPlan/CommanderPlan](https://github.com/Card-Forge/forge/blob/98d79231ccbe78f0083db907fdc875034665ba38/forge-ai/src/main/java/forge/ai/simulation/CommanderPlan.java). Audit the weakest-opponent assumptions in [StrategicEvaluator](https://github.com/Card-Forge/forge/blob/98d79231ccbe78f0083db907fdc875034665ba38/forge-ai/src/main/java/forge/ai/simulation/StrategicEvaluator.java): some terms select one opponent, while Commander needs the entire table considered. Existing multiplayer-aware terms should be preserved and extended. Do not implicitly treat all opponents as one perfectly cooperating team.

5. **Make information use explicit and fair.** Reuse and test [HiddenInfoShuffler](https://github.com/Card-Forge/forge/blob/98d79231ccbe78f0083db907fdc875034665ba38/forge-ai/src/main/java/forge/ai/simulation/HiddenInfoShuffler.java). Search may use its own known hand and legal public/revealed information. Define whether the experiment has open decklists; knowing a submitted opponent list is different from knowing its current hand or library order. Hidden-card permutations consistent with identical available information must not reveal a better action to the planner. A finite rollout sample also needs sensible belief sampling and a bounded memory budget.

   [Information-set MCTS research](https://eprints.whiterose.ac.uk/id/eprint/75048/) and [research on a Magic variant](https://eprints.whiterose.ac.uk/id/eprint/75050/) support investigating sampled hidden states and selective search. They do not establish that a particular implementation is strong across today's full Magic card pool or multiplayer Commander. Evaluate deeper ISMCTS only after bounded FlatMC and its evaluation/candidate generation are sound.

6. **Optimize Android execution independently of strategy.** Use [Perfetto/Android profiling](https://developer.android.com/topic/performance/inspecting-overview) to distinguish evaluation CPU, allocation/GC, blocked threads and initialization. Compare debug and a properly signed, non-debuggable performance build on the same physical OnePlus 8T, with matched compilation/thermal conditions. Capture [Baseline Profiles](https://developer.android.com/topic/performance/baselineprofiles/overview) for Forge initialization and actual AI hot paths in the child engine process, not only Compose startup. Validate R8 carefully because Forge uses reflection and resource-selected classes; do not enable shrinking without compatibility tests. Preserve the certificate used for updates. Faster compilation does not itself improve move quality, and documentation-level percentage gains are not a promised Forge speedup.

7. **Promote only demonstrated improvements.** First run deterministic tactical/legality checks, then a small smoke league, then a larger fixed-opponent league with held-out lists. For two-player games swap both decks and starting seats; for Commander rotate the candidate through all four seats against frozen opponents. Compare a candidate against the incumbent under equivalent resource conditions. Test all nine currently supported formats and representative archetypes; an aggregate gain can hide a control or combo regression. Respect BO3 sideboarding and format differences.

   Adapt upstream's [FlatMonteCarloBenchmark](https://github.com/Card-Forge/forge/blob/98d79231ccbe78f0083db907fdc875034665ba38/forge-gui-desktop/src/test/java/forge/ai/FlatMonteCarloBenchmark.java), which already balances two-player decks/seats, but keep MagicTester's separate error and timeout accounting. Report confidence intervals, tactical accuracy, legal-action violations, game completion, decision latency percentiles, allocation/PSS and thermal events. Predefine acceptable regressions and sample sizes; a few wins or self-play win rates alone do not demonstrate stronger play. Never silently drop failures or unfinished games from the evidence.

## Implementation checkpoint: November 8, 2026

The shared recorder and a first per-seat experimental `tactical-v1` policy are implemented under [`engine-ai/`](../engine-ai/README.md). The policy fixes tested simple multiplayer burn ranking cases behind an opt-in flag; native stable behavior remains the reference. Eleven native tactical positions and two completed transport/provenance games pass on a desktop JVM. This is a narrow heuristic correction, not the proposed FlatMC backport, trained model, complete decision corpus or a demonstrated overall playing-strength gain. See the module README for exact scope and evidence.

## First three reviewable changes

1. Shared AI policy/provenance schema, decision diagnostics and a small tactical corpus, without changing the default policy.
2. Shared/cooperative deadline and hot-path optimization work, with cancellation and state-consistency tests plus before/after profiles.
3. A pinned upstream-enhanced policy behind an experimental flag, followed by the balanced strength/performance comparison.

Subsequent changes expand the strategy matrix and mobile optimizations based on measured failures. Consider a small locally executed learned evaluator only after reliable training/evaluation data exists. A remote LLM dependency would conflict with the standalone/offline goal and is not necessary for these first improvements.

The [verified external gameplay-data review](research/MTG_GAME_DATA_REVIEW.md) adds a proposed Forge decision recorder and training-data foundation. It corrects the empty DraftZero corpus, partial human replay semantics, sample quality failures and source-specific licensing limits. External data should supplement verified Forge decisions rather than supply invented complete game states.
